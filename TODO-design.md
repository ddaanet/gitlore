Their typical case: a contributor clones the memory repos and submits a PR whose memory pin points at their own memory repo, with a module URL pointing at it too. Earlier probes: a branch checkout leaves memory's checkout alone and `git add -A` then records local memory HEAD; a merge where only their side moved the gitlink takes theirs silently; both sides moved stops with UU memory, unaffected by merge=ours, -X ours or ignore=all. Gaps: nothing stops a foreign gitlink landing on main, the parent-merge conflict has no documented resolution, nothing takes in fork memory. - A lost tier gitlink recorded only on memory's remote has no remedy once its recording checkout is gone: a take refuses the incoming commit (`gitlore_refuse_unresolvable_gitlinks` reads `origin/live:<tier>`), while `gitlore_resolve_check_pins` and `revert-pin` read only memory's index and local `live`, so `/gitlore:resolve` reports nothing and the user loops between it and `/gitlore:merge`. Probed (scratch /tmp/claude/gitlore-fanout/probe-lostpin.md): the loop reproduces and runs through `/gitlore:push` too. The merge refuses and names only the recording checkout's `/gitlore:push`; resolve exits 0 saying the state is healthy and to run `/gitlore:merge`; `revert-pin` says there is nothing to revert; a push or a memory commit from the second checkout hits the merge's refusal. The way out is by hand: fast-forward memory's `live` and HEAD to `origin/live`, after which `revert-pin` and the push work. The tooling's own push cannot produce the state; a raw push in memory, or a tier remote rewound and collected, does. Needs a design: no command gitlore prints leads out.
